# 周复盘 DIY 手册（无 AI 期间版）

> 背景：订阅断档期间，周日复盘没有 AI 替你总结"进步 / 薄弱 / 下周重点"。
> 本手册把原来靠"全程交互记录"才能做的评审，拆成**可自己采集的数据源 + 固定流程**。
> 每周日 60-90 分钟，照着走即可。续费后可以把产出直接喂回给 AI 复核。

---

## 核心思路

原来 AI 的优势是"记得你全程怎么错的"。断档期间用三个数据源替代记忆：

| 数据源 | 替代什么 | 怎么用 |
|---|---|---|
| **git log 的 wip 演进** | "代码如何变化" | 用 diff 找设计变化和修正过程；提交次数不能推断独立程度或提示次数 |
| **NOTES.md 自评节** | "哪里最没底、哪里靠提示" | 这是你自己当天写的，最诚实，直接汇总 |
| **ANSWER.md 的错误对照** | "还需要验证的边界" | 对照常见错误写法，记录能否解释并自行构造反例；没有踩过不代表侥幸，也不代表掌握 |

---

## 流程（周日晚，60-90 分钟）

### 第一步：采集（15 分钟，纯机械）

```bash
# 本周各 day 的提交轨迹（回顾设计变化）
git log --oneline --since="上周一" -- src/

# 每天的自评
cat src/dayXX/NOTES.md | grep -A 3 "自评"
```

填一张表（写在草稿上即可）：

| Day | 提示次数及来源（未记录则注明） | 自评关键词 | 边界解释结果 | 隔天／周末重做结果 |
|---|---|---|---|---|
| ... | ... | ... | ... | ... |

### 第二步：5 分钟重做法（每周必做，最防自欺）

从本周的 day 里**随机挑一个**，不看自己 solution.ts 和 ANSWER.md，
只看 README 题面，重写其中**最核心的一个类型**（不是全部，5 分钟以内）。

- 写得出 + `pnpm check:day XX` 过 + 能解释关键设计 → 记录为本次独立重做通过
- 卡壳 / 写错 → 在表格"重做测试"列记 ✗，这就是下周要重做的 day

> 原理：看懂答案和自己长出来是两回事。一周一次抽样重做，是最便宜的自检。

### 第三步：写复盘（30 分钟，格式沿用 W1）

写进 `PROGRESS.md`，格式与 W1 周复盘完全一致：

```markdown
## 周复盘 · WX(Day A-B,日期)

### 进步的地方
1. **一句话概括能力点** —— 证据:Day X 的某段代码/某个 commit 现象

### 仍然薄弱的模式(按出现频次排序)
1. **模式名** —— 出现在 Day X、Day Y 两处;对策:一句话可执行动作

### 下周重点(Day C-D)
- 具体 day + 具体概念 + 怎么验证自己过关
```

**写"进步"的纪律**：每条必须带证据（哪天哪段代码），没证据的进步删掉——防止漂亮流水账。

**写"薄弱"的纪律**：按本周**出现频次**排序，不按"感觉难易"。每条必须带：
- 至少一个具体实例（哪天哪道题）
- 一句可执行的对策（参考 W1 的"把测试断言原文贴在旁边逐字符对照"这个粒度）

### 第四步：产出下周行动（10 分钟）

从薄弱模式推导下周重点，每条写清**验证标准**（什么叫过关）：

- ✗ 坏写法："下周复习泛型"
- ✓ 好写法："Day 23 的 DeepReadonly 不看答案重写，两个 @ts-expect-error 反例能说出为什么"

## 卡住时的求助阶梯（替代"问 AI"）

1. `docs/TS-ERROR-CHEATSHEET.md` —— 按错误码/主题查，10 分钟
2. 该 day 的 `ANSWER.md` **第二节（常见错误写法）** —— 只看错误对照，不看参考实现
3. 还不行 → 看完整参考实现，但**合上后重写一遍**（不是抄一遍）
4. 标记到 NOTES.md 自评节"哪里靠提示才过"，下周复盘进表格

## 断档期节奏建议

- 工作流第 2-4 步（点评循环）天然失效，用"写完 → 测试全绿 → 隔 30 分钟再对照 ANSWER.md"替代：
  冷却半小时再对照，能区分"真会"和"刚写完的记忆"
- NOTES.md 其余部分照常自己写；「自评」节照常自填（这本来就归你）
- JSDoc：Day 19 起本就规划"你写你评"渐进移交，断档期正好全量自己写——文档即 API 设计
- 每天的 PROGRESS.md 一句话收获照常——续费后这是 AI 恢复上下文的第一入口
