# 与 chipRunner 衔接的业务迁移练习

更新：2026-10-06。默认仍按[从 Day 1 重学的顺序](./LEARNING-ORDER.md)推进，本页提供穿插实践，不要求先完成全部 TS 课程。chipRunner 的项目目标见[学习地图第四节](../../chipRunner/docs/learning-map.md#四能力训练与上线维护2026-10-06)。

## 两种实践方式，选一种即可

- **本仓库小实验**：在对应 day 新增 `transfer.ts` / `transfer.test.ts`，先自己设计，再用 `pnpm check:day XX` 检查。该命令覆盖整题；原题未完可能失败，须记录哪些错误属于未完成部分，不能声称整题全绿。
- **真实项目实践**：在 chipRunner 的真实需求中理解、修改和验证，记录文件/函数或提交链接、验证结果及本人完成部分，不必把 Nuxt 代码复制进裸 TS 练习仓库，也不要求导入 Nuxt 环境才能做小实验。

同主题已有真实项目改动且本人独立完成关键部分、给出相关验证证据时，可以替代迁移题及后续重复重做，不再额外写相似 transfer。只有阅读、当天照抄、AI 代写后看懂，记录为阅读或辅助实现，不能填“独立迁移通过”。若同一天完成，需要后续换场景独立验证，才可替代隔天重做的证据。

项目迁移不替代 tstest 原题的类型检查和运行时测试，也不改变整题完成标准。下面节点按知识关联，不是必须等到某一天才能做项目的闸门。

## Day 1–2：认识消息与工具的类型

入口：[useChat.ts](../../chipRunner/app/composables/useChat.ts) 中的 `ChatMessage`、`ToolCall`，以及 [ToolCard.vue](../../chipRunner/app/components/ToolCard.vue)。

- 找出 role、工具 status、content、result、error 分别描述什么，观察 UI 根据哪些字段展示。
- 画出一个成功调用和一个失败调用的数据例子，不必重写整个状态机。
- 解释：`status` 是联合类型，是否就保证了 result 一定存在？类型字段和业务约束有什么差别？
- 证据：自己的例子及解释。此时完成阅读也有价值，但不等于已独立实现。

## Day 3–4：理解会话恢复与守卫

入口：[sessionStore.ts](../../chipRunner/app/utils/sessionStore.ts) 的 `loadSessions` 和类型守卫，以及 [session.ts](../../chipRunner/app/types/session.ts)。

- 追踪 JSON 解析后如何验证形状，再进入业务代码。
- 构造合法数据、缺字段、字段类型错误三个脱敏小样本，观察实际守卫或公开读取入口的处理结果。
- 解释：TS 接口、`as` 和运行时守卫各自能保证什么；已有守卫具体检查了哪些层。
- 只使用内存替身或隔离测试数据，不覆盖浏览器里的真实会话。无需修改项目后端或引入校验库。

## Day 5–7：比较三种数据形状

入口：`ChatMessage`（界面）、`StoredMessage`（持久化）、`WireMessage`（请求），沿 `toStored` → 存储 → `hydrate` → `toWire` 阅读。

- 列出各自需要哪些字段、为什么有的字段不保存、有的字段要转换。
- 为一个简化业务例子设计转换函数或写出输入输出；不强制用泛型或 Pick/Omit 替代本来清楚的独立模型。
- 解释：成功/失败是过程状态还是会影响下次请求的结果？为什么“已结束”不等于“成功”？
- 可选保留原 Day 6 事件题：开始携带 ID/输入、成功携带输出、失败携带错误；类型反例验证事件名与载荷的关联。与项目已验证同主题时不用重复做。

## Day 10：把状态设计用于真实问题

优先衔接 chipRunner 的“工具失败状态保存与恢复”，动手前确认当前问题是否仍存在；如果已经修好，选一个未验证的边界或取消状态作为变化需求，不重复制造缺陷。

- 定义哪些最终状态需要保存、旧会话缺字段时怎样兼容。
- 验证失败 → 保存 → 恢复后的界面含义，以及下一次请求中的失败标记；保留成功与旧数据路径。
- 解释：类型限制了什么，运行时状态转移还需检查什么。
- 若暂不改项目，可做原流式状态小实验：等待、接收中、完成、失败，验证片段追加、空片段与结束后再次操作。两种方式选一。

## Day 15：composable 的输入与输出

入口：[useChat.ts](../../chipRunner/app/composables/useChat.ts) 以及 [ChatWindow.vue](../../chipRunner/app/components/ChatWindow.vue)。

- 列出组件消费的状态、动作和生命周期清理职责。
- 选择一个真实交互变化或隔离小实验，说明输入如何影响返回状态、失败如何反馈。
- 验证所改行为；不为套题目签名而重写 useChat，也不以纯 TS 模拟代替真实 Vue 生命周期验证。

## Day 17：会话 API（可选补充）

项目已有相关请求改进证据时直接复用；否则以 mock transport 练“获取列表 / 获取单条”的参数、响应与错误类型。

- 类型验收：请求参数、响应和调用点推导一致，非法参数被拒绝。
- 运行时验收：成功、业务失败、transport 抛错。
- 解释：泛型声明能否证明服务器实际返回的数据符合预期？不要为了练习强行给 chipRunner 增加服务端会话系统。

## Day 25：外部数据校验

当前默认路线中 Day 25 在 Day 17 之后。可以在 Day 17 的模拟接口、已有真实接口或本地存储数据中选择一个，输入从 `unknown` 开始；未做可选 API 题也不影响这里练习。

- 类型验收：校验后的业务类型由 schema 推导。
- 运行时验收：合法数据、缺字段、类型错误、额外字段的处理策略。
- 解释：与现有手写守卫相比，schema 的收益和成本是什么，校验失败如何传给调用方？
- Zod 在本仓库练习；迁入 chipRunner 前遵守其依赖约定，不因练过一个库就替换所有守卫。

## Day 29：一次有边界的重构

从真实项目选一处类型或职责问题，先列出需要保持的行为和允许修复的缺陷，再小步修改与验证。若此前状态修复已包含同样的独立设计、兼容处理和回归证据，可直接引用，不必再造一次重构。
